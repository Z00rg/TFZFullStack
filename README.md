# Калькулятор ТФЗ

Фуллстек-приложение для расчёта интегрального показателя тяжести токсических
форм зоба. Фронтенд и API живут в одном проекте Next.js и разворачиваются на
Vercel целиком — отдельного бэкенда на Django больше нет, весь его функционал
перенесён сюда.

## Стек

| Слой | Решение | Почему |
| --- | --- | --- |
| Приложение | Next.js 15 (App Router) | Страницы и API в одном деплое |
| База данных | Postgres (Neon) + Drizzle ORM | HTTP-драйвер не держит соединений — подходит serverless |
| Кэш и сессии | Redis (Upstash) | REST-клиент работает из serverless-функций без TCP |
| Аутентификация | JWT в httpOnly-куках (`jose`) | Проверяется на edge, в middleware |
| Пароли | scrypt из `node:crypto` | Memory-hard, без нативных зависимостей |
| Валидация | Zod | Один источник правды для проверок и OpenAPI |

## Устройство

```
src/
  app/
    api/            — route handlers (бывшие Django-вьюхи)
    admin-home/     — административный раздел
    api-docs/       — документация API (замена swagger-ui)
  server/           — серверный код, в клиентский бандл не попадает
    db/             — схема и подключение к Postgres
    auth/           — пароли, JWT, сессии, проверка прав
    http/           — ответы, ошибки, защита от CSRF
    redis/          — клиент и ограничение частоты запросов
    services/       — бизнес-логика и работа с данными
    validation/     — Zod-схемы (бывшие сериализаторы DRF)
    openapi/        — сборка OpenAPI-документа
  entities/         — запросы react-query
  features/         — пользовательские сценарии
  shared/           — API-клиент и UI-кит
drizzle/            — SQL-миграции
scripts/seed.ts     — создание первого администратора
```

## Локальный запуск

Нужен Node 22+.

```bash
npm install
cp .env.example .env.local   # заполните DATABASE_URL и JWT_SECRET
npm run db:migrate           # создаёт таблицы
npm run db:seed              # создаёт главного администратора
npm run dev
```

`JWT_SECRET` можно сгенерировать так:

```bash
openssl rand -base64 48
```

В качестве базы подойдёт и бесплатный Neon, и локальный Postgres: драйвер
выбирается по строке подключения автоматически (переопределяется переменной
`DB_DRIVER` со значением `neon` или `pg`).

Без переменных Upstash локально включается in-memory заглушка Redis — её хватает
для разработки. В продакшене приложение без Redis не стартует: сессии и счётчики
попыток входа разъехались бы между инстансами функций.

Полный локальный стенд с Postgres и Redis в контейнерах:

```bash
JWT_SECRET=$(openssl rand -base64 48) docker compose up
```

## Деплой на Vercel (бесплатный тариф)

1. **Создайте проект.** Импортируйте репозиторий на [vercel.com/new](https://vercel.com/new).
   Next.js определится сам, менять настройки сборки не нужно.

2. **Подключите Postgres.** В проекте → **Storage** → **Create Database** →
   **Neon**, тариф Free. Vercel сам добавит `DATABASE_URL` в переменные
   окружения проекта.

3. **Подключите Redis.** Там же **Create Database** → **Upstash for Redis**,
   тариф Free. Vercel добавит `KV_REST_API_URL` и `KV_REST_API_TOKEN` —
   приложение понимает и эти имена, и «родные» `UPSTASH_REDIS_REST_*`.

4. **Добавьте секрет.** В **Settings → Environment Variables** создайте
   `JWT_SECRET` (минимум 32 символа) для всех окружений.

5. **Примените миграции.** С локальной машины, подставив строку подключения
   к созданной базе:

   ```bash
   vercel env pull .env.local
   npm run db:migrate
   npm run db:seed
   ```

   Для миграций лучше брать прямое подключение без пулера — интеграция Vercel
   кладёт его в `DATABASE_URL_UNPOOLED`. Если `vercel env pull` недоступен,
   скопируйте строку из панели Vercel в `.env.local` вручную и допишите туда же
   `JWT_SECRET` и данные `SEED_SUPERADMIN_*`.

6. **Проверьте деплой.** Откройте `https://<ваш-проект>.vercel.app/api/health` —
   должно вернуться `{"status":"ok","checks":{"database":"ok","redis":"ok"}}`.

Чтобы сократить задержки, в **Settings → Functions** выберите регион рядом с
регионом базы Neon.

## Переменные окружения

| Переменная | Обязательна | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | да | Строка подключения к Postgres (можно `POSTGRES_URL`) |
| `JWT_SECRET` | да | Подпись токенов, минимум 32 символа |
| `UPSTASH_REDIS_REST_URL` | в продакшене | REST-адрес Redis (можно `KV_REST_API_URL`) |
| `UPSTASH_REDIS_REST_TOKEN` | в продакшене | Токен Redis (можно `KV_REST_API_TOKEN`) |
| `ACCESS_TOKEN_TTL` | нет | Время жизни access-токена, по умолчанию `15m` |
| `REFRESH_TOKEN_TTL` | нет | Время жизни refresh-токена, по умолчанию `7d` |
| `LOGIN_RATE_LIMIT` | нет | Попыток входа в окно, по умолчанию `5` |
| `LOGIN_RATE_WINDOW_SECONDS` | нет | Длина окна в секундах, по умолчанию `60` |
| `DB_DRIVER` | нет | Принудительный выбор драйвера: `neon` или `pg` |
| `BUILD_STANDALONE` | нет | `true` — сборка для Docker-образа |

## Аутентификация

Вход выдаёт две httpOnly-куки: короткоживущий `access` (JWT, 15 минут) и
`refresh` (7 дней). Токены недоступны из JavaScript, поэтому XSS не уводит
сессию.

Refresh-токен одноразовый: при каждом обновлении выдаётся новый, а старый
удаляется из Redis. Если приходит уже использованный токен — значит он,
вероятнее всего, украден, и все сессии пользователя гасятся. Вместе с номером
поколения сессий в аккаунте это обесценивает и уже выданные access-токены, так
что отзыв срабатывает немедленно.

Отдельного CSRF-токена нет. Его заменяют `SameSite=Lax` на куках и сверка
заголовка `Origin` для всех небезопасных методов — тот же подход, что Next.js
применяет к Server Actions.

## Роли

| Роль | Права |
| --- | --- |
| `WORKER` | Пациенты и расчёты |
| `ADMIN` | То же плюс список сотрудников |
| `SUPERADMIN` | То же плюс создание администраторов |

Первый `SUPERADMIN` создаётся через `npm run db:seed`, дальше администраторов
заводят из раздела «Администрирование».

## API

Полная схема — на странице `/api-docs` (нужен вход в систему), машиночитаемая
версия — `/api/openapi`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/login` | Вход |
| `POST /api/auth/logout` | Выход |
| `POST /api/auth/refresh` | Обновление сессии |
| `POST /api/auth/register/worker` | Регистрация сотрудника |
| `POST /api/auth/register/admin` | Создание администратора |
| `POST /api/auth/register/superadmin` | Создание главного администратора |
| `GET /api/profile` | Текущий пользователь |
| `GET,POST /api/patients` | Список и создание пациентов |
| `GET,PATCH,DELETE /api/patients/{id}` | Карточка пациента |
| `POST /api/patients/{id}/calculate` | Выполнить расчёт |
| `GET /api/patients/{id}/calculations` | История расчётов (фильтр `?mode=`) |
| `GET,DELETE /api/calculations/{id}` | Отдельный расчёт |
| `GET /api/worker-profiles` | Сотрудники (ADMIN и выше) |
| `GET,PATCH,DELETE /api/worker-profiles/{id}` | Профиль сотрудника |
| `GET /api/health` | Проверка Postgres и Redis |

## Отличия от прежней версии на Django

Логика расчёта перенесена дословно — пороги, веса и формулировки рекомендаций
совпадают. Остальное изменилось осознанно:

* **Пол пациента теперь влияет на результат.** В Django в поле расчёта
  записывался числовой код пола (`0`/`1`), а сравнивался он со строкой
  `"male"` — условие никогда не выполнялось. Из-за этого терялся балл за
  мужской пол и исчезал соответствующий довод в рекомендации по ДТЗ.
* **Даты отдаются в ISO 8601**, а не в формате «ДД.ММ.ГГГГ». Так их можно
  сортировать и сравнивать; под локаль строка приводится в интерфейсе
  (график истории раньше сортировался неверно именно из-за этого).
* **Токены не возвращаются в теле ответа** — только в httpOnly-куках.
* **Роль читается из подписанного токена**, а не из обычной куки `user_role`,
  которую можно было изменить из консоли браузера.
* **Админка Django заменена** разделом `/admin-home`: сотрудники и создание
  администраторов. Данные пациентов и расчётов правятся из основного
  интерфейса врача.

Удаление пациента по-прежнему доступно любому аутентифицированному
пользователю — как и раньше. Учтите, что оно каскадом удаляет всю историю
расчётов; чтобы ограничить это администраторами, замените `requireUser` на
`requireAdmin` в `src/app/api/patients/[id]/route.ts`.
